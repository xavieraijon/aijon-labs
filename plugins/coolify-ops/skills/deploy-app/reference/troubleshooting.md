# Troubleshooting

Learned deploying real apps with Coolify v4.6 on a Raspberry Pi 5 (ARM64) and applicable to any server.

| Symptom | Cause | Fix |
|---|---|---|
| 502 / 503 / «no available server» | The app listens on `127.0.0.1`/`localhost`, or Coolify's port (`ports_exposes`) differs from the app's | Listen on `0.0.0.0`; the Dockerfile `EXPOSE` and `--port` must match |
| The deployment fails although the app works | Coolify health check enabled on a `slim`/`alpine` image without `curl` or `wget` | Keep `health_check_enabled=false` (what `create-app` does) or install `curl` in the image. The Python templates have their own `HEALTHCHECK` (a TCP connect run with Python), which Coolify honours even with its check off |
| Old Angular builds fail with OpenSSL or dependency errors | Angular 12 needs Node 14, 13–14 Node 16, 15–16 Node 18 | `analyze.py` picks Node from the Angular version; force another with `prepare.py <path> --var NODE_VERSION=16 --overwrite` |
| Reloading an SPA route (e.g. `/cart`) returns 404 | The server does not fall back to the app shell | The SPA template's `nginx.conf` uses `try_files $uri $uri/ /<fallback>`; the fallback depends on the framework (see the row on nginx fallbacks below) |
| Angular ≥ 17 outputs to `dist/<app>/browser` | The `application` builder adds `/browser` | `analyze.py` accounts for it; check `BUILD_DIR` if the build folder is not found |
| Angular SSR answers 400 «URL with hostname … is not allowed» | `@angular/ssr` only serves hosts listed in `NG_ALLOWED_HOSTS` (or `security.allowedHosts` in `angular.json`); there is no default | `create-app --env-domain NG_ALLOWED_HOSTS` sets it to the app's domain (`env-domain <app> NG_ALLOWED_HOSTS` after a domain change); for the local check pass `--env NG_ALLOWED_HOSTS=localhost,127.0.0.1` |
| SvelteKit form actions fail with «Cross-site POST form submissions are forbidden» | SvelteKit compares `Origin` with the URL it builds; behind a proxy it needs the forwarded headers | The `node-ssr` template sets `PROTOCOL_HEADER`/`HOST_HEADER`. Coolify's Traefik replaces client-supplied `X-Forwarded-*`; with another proxy in front (Caddy, a CDN, a tunnel) make sure it does too, or set `ORIGIN=https://<domain>` instead |
| SvelteKit/Astro/Nuxt project blocked: adapter or preset «cannot run on a plain server» | Built for another platform (`adapter-auto`, `@astrojs/vercel`, `NITRO_PRESET=vercel`…) | Switch to the Node adapter (`@sveltejs/adapter-node`, `@astrojs/node` with `mode: 'standalone'`, default Nitro preset) or to the static one; the skill never changes it for you |
| React Router form actions answer 400 «The `request.url` origin does not match `origin` header» | `react-router-serve` does not trust the proxy, so behind HTTPS it sees `http://` and the browser's `Origin` (`https://`) does not match | Add `allowedActionOrigins: ["<domain>"]` to `react-router.config.ts` (code change: only if the user asks) and redeploy |
| Astro (server) answers 403 «Cross-site POST form submissions are forbidden» to its own forms | Astro trusts `X-Forwarded-Proto` only for hosts in `security.allowedDomains`; otherwise it sees `http://` and `checkOrigin` fails | Add `security: { allowedDomains: [{ hostname: "<domain>", protocol: "https" }] }` to `astro.config.*` (code change: only if the user asks) and redeploy |
| The build fails: a variable imported from `$env/static/private` is missing | SvelteKit inlines `$env/static/*` at build time | `env-push --buildtime <KEY…>` (`create-postgres --buildtime` for `DATABASE_URL`). Coolify adds `ARG` lines after every `FROM` and passes the values as build arguments: they are not shown in the logs but stay in the image history on the server. Locally `local_check.py --build-env KEY=<test value>` |
| `npm ci` fails in the second stage of an SSR image (`nuxt prepare`, `svelte-kit sync`) | Install hooks run without sources or dev tools | The `node-ssr` template installs with `--ignore-scripts`; regenerate the Dockerfile if it is older |
| Reloading a route of a static site returns the home page instead of 404, or a deep link of an SPA returns 404 | Wrong nginx fallback for the kind of site | `prepare.py` writes the SPA conf (fallback `index.html`, `200.html`, `index.csr.html` or `__spa-fallback.html`) only for SPAs, and the multi-page conf (with `404.html`) otherwise |
| Django answers 400 Bad Request (DisallowedHost) on its domain | `DJANGO_ALLOWED_HOSTS` is missing or holds an old domain | `env-domain <app> DJANGO_ALLOWED_HOSTS` (also after a domain change), then redeploy. `coolify_settings.py` always adds `localhost` and `127.0.0.1` |
| Django answers 403 «CSRF verification failed. Origin checking failed» | Django does not see the request as HTTPS, so `Origin` (`https://…`) does not match | `coolify_settings.py` trusts `X-Forwarded-Proto` (`SECURE_PROXY_SSL_HEADER`). Coolify's Traefik replaces client-supplied `X-Forwarded-*`; with another proxy in front (a CDN, a tunnel) make sure it sets that header, or add the domain to `CSRF_TRUSTED_ORIGINS` |
| The Django build fails at `collectstatic` (`KeyError`, `ImproperlyConfigured`) | The project's settings read a variable with no default when imported, and build time has no variables (only a dummy `DJANGO_SECRET_KEY`) | The analysis lists them in a warning: give them a default in the settings (code change: only if the user asks). `collectstatic` never connects to the database |
| A Django deployment «failed» and the previous version is still online | The new container never became healthy: a migration failed (or the app did not import) and Coolify kept the old one | The deployment log (`wait <deployment_uuid> --lines 120`) has the new container's output: the traceback after `Applying …` (`logs <app>` shows the old container, still running). Fix the migration in the project and push again; PostgreSQL rolls back a failed migration, but earlier ones of the same run stay applied |
| Files uploaded to a Django app disappear after a deploy | `MEDIA_ROOT` is inside the container, which is replaced on every deploy | Use object storage (e.g. django-storages) or a persistent volume added in Coolify by hand |
| Admin pages without CSS | `collectstatic` did not run or WhiteNoise is not active | Check that `django.contrib.staticfiles` is installed and that the Dockerfile has the `collectstatic` line (regenerate with `prepare.py --overwrite`); with remote static storage run `collectstatic` yourself |
| A Laravel page has no styles or scripts (mixed content), links and redirects use `http://` | Laravel trusts no proxy by default, so behind Coolify's HTTPS it builds `http://` URLs | `config/trustedproxy.php` (generated by `prepare.py`) with `TRUSTED_PROXIES=*` from the image; if the project sets `trustProxies` itself, use `at: '*'`. Check with `verify.py --expect https://<domain>/build/` |
| Laravel answers 419 «Page Expired» to forms | Session cookie not kept: `APP_KEY` changed, or a secure cookie over plain HTTP | Never rotate `APP_KEY` (`env-generate` keeps it); the image sets `SESSION_SECURE_COOKIE=true`, so test over HTTPS |
| Laravel 500 «No application encryption key has been specified» | `APP_KEY` is missing | `coolify.py env-generate <app> APP_KEY:laravel` and redeploy |
| A Laravel deployment «failed» and the previous version is still online | The new container never became healthy: `php artisan migrate` or `optimize` failed at start | Read the deployment log (`coolify.py wait <deployment> --lines 120`): `FAIL`/`QueryException` after `Running migrations` = migration; an exception after `Caching` = route/view/config cache (e.g. duplicate route names). Fix the project and push |
| The Laravel build fails in `composer dump-autoload`, `package:discover` or `wayfinder:generate` | A service provider needs the database or a variable while booting; the build has neither | Move that code out of `boot()` (or guard it with `app()->runningInConsole()`) |
| Laravel queued jobs never run, scheduled tasks never fire | Only the web process is deployed | `QUEUE_CONNECTION=sync` runs jobs inline; a worker or scheduler needs a second app with its own start command (not covered yet) |
| Laravel behind another proxy in front of Coolify (Cloudflare proxy, a load balancer) gets wrong client IPs or hosts | `TRUSTED_PROXIES=*` trusts the nearest proxy, Traefik, which forwards what it received | Keep Traefik as the only proxy, or set `TRUSTED_PROXIES` to the real proxy addresses |
| `uv sync --locked` fails: the lockfile needs a newer uv | `uv.lock` was written by a newer uv than the one pinned in the Dockerfile (`ghcr.io/astral-sh/uv:<version>`) | Raise that version in the Dockerfile, or regenerate the Dockerfile after updating the plugin |
| A Python build fails installing `psycopg2` | It must be compiled and the slim image has no compiler or `libpq` | Use `psycopg2-binary` or `psycopg[binary]` (the analysis blocks plain `psycopg2`; plain `psycopg` gets `psycopg[binary]` added) |
| `NEXT_PUBLIC_*` / `VITE_*` variables are empty in the browser | They are inlined at build time; runtime-only variables never reach the bundle | `env-push` also marks them for build time |
| No HTTPS certificate | Let's Encrypt needs ports 80 and 443 reaching the server and DNS pointing at the public IP | `verify.py` waits up to 2 minutes; then check router/firewall ports and DNS |
| Traefik does not retry a certificate after opening the ports | Traefik does not retry while its configuration is unchanged | Restart Coolify's proxy (`docker restart coolify-proxy` on the server) |
| `git push` blocked from Claude Code | By design | The user runs the command with `!` |
| GitHub webhooks never arrive | The GitHub App's Webhook URL points to a private address | GitHub → Developer settings → GitHub Apps → the app → public Webhook URL (path `/webhooks/source/github/events`) |
| The API returns 401 | Invalid, expired or mistyped token | Create a new token and store it again (Keychain service `coolify-api-token`, or `~/.config/coolify-ops/token`) |
| Coolify installed but unhealthy (`installed-unhealthy`, containers restarting) | Usually not enough RAM/disk, or a port (80, 443, 8000) already taken by another service | `server.py health --ssh …` shows which containers fail; free the port or resources; then the user (not Claude: it needs sudo) re-runs the official install command in their own ssh session, which repairs it in place |
| The API returns 403 | The client IP is not in «Allowed IPs» or the token lacks a permission | Settings → Advanced → API access; token with `read`, `read:sensitive`, `write`, `deploy`, `delete` |
| `logs` returns 403 «Missing required permissions: read:sensitive» | Coolify requires `read:sensitive` to read logs | Create a new token including it (permissions cannot be edited) |
| 403 «Missing required permissions: delete» | `delete` is separate from `write` | Create a new token including it (permissions cannot be edited) |
| Volumes, images or folders left on the server after deleting | Coolify marks the resource deleted at once (the API already answers 404) and cleans the server in a background job a second later. If the project is deleted in between, the job fails with «Attempt to read property "project" on null» and leaves everything behind | `decommission` watches the server over ssh until no containers or volumes with the uuid remain, and only then deletes the project (without ssh it waits 45 s); then it removes the app's own images (named after its uuid), which Coolify keeps. Old leftovers: `docker volume rm`, `docker image rm` and, with sudo, `/data/coolify/{applications,databases}/<uuid>` |
| The API does not answer | Not on the server's network/VPN, or API access disabled | Connect the VPN or enable API access |
| A deployment interrupts a long-running task in the app | Every deployment restarts the container | For apps with long tasks, create with `--no-autodeploy` and deploy manually |
| The server gets hot while building | Heavy Node/Angular builds | Normal for 1–2 minutes; if it often exceeds 80 °C, improve cooling |
